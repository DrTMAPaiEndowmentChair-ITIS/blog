_Updated September 25, 2026 with technical examples and source references. Original publication date retained._

A coding model is unusually good at finding performance wins when it can run the program, inspect a profile, change one thing, and measure again. Anthropic's [account of making claude.ai faster](https://claude.dev/blog/how-we-made-claude-ai-faster/#anything-can-be-hill-climbed) makes the case through ordinary product work: identify a user journey, build a local measurement that tracks it, and keep lowering the number. The team's reported gains belong to its own app and setup. The reusable part is the loop.

## Choose the number carefully

Start with a real user action: opening a large project, sending a message, searching a mailbox, loading a report, or starting a model session. Record a baseline distribution, including p50 and p95, on fixed hardware and realistic data. Save a correctness check before editing. A faster result that skips work or changes the answer is a regression.

The inner loop can be simple:

```text
reproduce -> profile -> propose one change -> run correctness checks
          -> repeat benchmark -> inspect diff -> keep or revert
```

Ask the model to report the bottleneck it measured, the proposed mechanism, and the before/after result. Keep benchmark inputs fixed during a run. Recheck promising changes against a second dataset so the model cannot merely tune for one fixture.

Anthropic used instruction counts on two hot paths because they were less noisy than wall-clock timing, then checked that lower counts also reduced elapsed time. That last check matters. An easily optimized proxy can drift away from what people feel. If an agent discovers that the benchmark ignores parsing, it may remove parsing from the measured path while leaving the application no faster.

## Different software, different climbs

| Workload         | Measure                                              | Likely bottlenecks                                     | Correctness gate                      |
| ---------------- | ---------------------------------------------------- | ------------------------------------------------------ | ------------------------------------- |
| Web app          | Time to usable input, long-task time, p95 navigation | Hydration, rerenders, bundle loading, main-thread work | Browser interaction and visual checks |
| CLI              | Cold start and task completion time                  | Module loading, subprocesses, repeated parsing         | Exact output and exit status          |
| Database service | p95 query latency at a fixed arrival rate            | Plans, indexes, N+1 calls, serialization               | Query result comparison               |
| Model server     | Goodput under TTFT and TPOT limits                   | Batching, KV memory, prefill scheduling                | Output-quality and SLO checks         |
| Data pipeline    | Records per second and total completion time         | I/O, allocation, compression, skew                     | Counts and sampled records            |

The prompt should describe the workload, not prescribe a clever optimization. "Reduce p95 open time on this 10,000-item fixture while preserving all visible items" gives the model room to find a bad algorithm. "Add memoization" may lock it onto the wrong fix.

## Make the climb trustworthy

Run the benchmark several times. Control caches, warmup, parallel load, and build mode. Record the command, commit, machine, and input. For a server, test at several arrival rates; an optimization that helps one request can worsen queueing at production load. For a UI, profile a slower laptop as well as a fast developer machine.

Keep changes small enough to review. A model can land a series of modest wins, but each should survive tests and a real user path. Add a regression threshold only after the metric has proved stable and correlated with elapsed time. If the metric flakes, fix or remove it.

## Start with a contract the agent cannot quietly change

A performance task should specify the user journey, representative input, start and end events, required behavior, and resource constraints. The contract is more important than the first optimization idea. If "open project" ends when a spinner appears, the benchmark rewards showing a spinner quickly rather than making the project usable.

For example:

```text
Journey: open a project containing 10,000 records.
Start: the user activates its link.
End: the visible records are rendered and the search field accepts input.
Behavior: preserve sorting, selection, keyboard navigation, and result counts.
Objective: reduce p95 duration without increasing peak memory by more than 10%.
Evidence: trace, benchmark samples, correctness results, and a reviewable diff.
```

These are example constraints, not results from this site. Keep the benchmark and its fixtures outside the agent's permitted optimization scope unless a reviewer explicitly accepts a correction. A model can otherwise improve a number by shortening the fixture, weakening the assertion, or moving the end marker earlier.

Browser User Timing marks allow application-specific intervals rather than relying only on generic page-load metrics.[^timing] Put the end marker at the actual readiness condition. Scheduling a callback does not prove that a frame has painted, and receiving data does not prove that the interface can process input.

## Use a profile to choose the first experiment

Break elapsed time into work and waiting. CPU samples can identify a repeated parser, while a timeline may reveal sequential network calls or a blocking subprocess. A hot function is not automatically on the user journey's critical path. Conversely, waiting can dominate without producing many CPU samples.

Brendan Gregg's USE method asks about utilization, saturation, and errors for system resources.[^use] Apply that distinction before asking for a rewrite. A saturated CPU needs a different intervention from an idle CPU waiting on storage. High memory use is different from allocation churn, and a low average can conceal a short burst that blocks input.

An illustrative 500 ms operation might spend 300 ms parsing, 150 ms waiting for data, and 50 ms rendering. Making parsing twice as fast reduces the total to 350 ms, a 1.43x improvement. Even eliminating rendering completely can save only 50 ms. This simple upper-bound calculation helps reject elaborate ideas aimed at the wrong part of the path.

Ask for a mechanism before accepting a change: "build an index once so each lookup avoids scanning all records" is testable. "Use a faster data structure" is too vague until it names the repeated operation, cost, and lifecycle.

## Write the experiment log before running a search

Keep one row per candidate, including failures:

| Candidate       | Hypothesis                     | Correctness gate                  | Timing result                      | Decision                                |
| --------------- | ------------------------------ | --------------------------------- | ---------------------------------- | --------------------------------------- |
| Cached index    | Remove repeated linear scans   | Compare result IDs and order      | Record raw samples                 | Keep only if stale-data cases pass      |
| Deferred parser | Move work off the opening path | Verify content before interaction | Measure both opening and first use | Reject if delay merely moves to typing  |
| Larger batch    | Amortize fixed overhead        | Verify cancellation and errors    | Include tail latency               | Reject if interactive deadlines regress |

Run baseline and candidate measurements in alternating order where practical. Otherwise thermal throttling, cache warming, or a background job can align with one version. Warm a JIT before a steady-state comparison, but retain a separate cold-start benchmark when startup matters to users.

Save individual samples. A median alone cannot reveal a multimodal distribution. Do not delete slow runs without a recorded reason that applies equally to both versions. If a difference is comparable to run-to-run noise, gather more evidence or report it as inconclusive.

Percentiles need enough observations to be meaningful. A p95 from twenty runs is determined by roughly the slowest one or two observations, depending on the estimator. Reporting that value to three decimal places does not create precision. Record sample count and use a stable workload before turning a percentile into a release gate.

## Prevent a proxy from replacing the objective

Instruction counts, allocation counts, DOM mutations, and database queries can be useful stable proxies. Their relationship to elapsed time must be demonstrated. Fewer instructions can still lose if the remaining work waits on memory; fewer queries can lose if one enormous query transfers much more data.

Anthropic's September 23 account describes validating local performance metrics against user-visible latency and rejecting metrics that did not support that relationship.[^claude] The lesson is methodological. Its reported gains do not establish the result of a similar change in a different application.

Use a second fixture that differs in size or shape from the optimization fixture. If a parser gets faster only for ASCII input, test multilingual and mixed-format input. If memoization wins, test edits that should invalidate the cache. If virtualization wins, test keyboard focus, search, and assistive technology access to the content users need.

## Evaluate the system under load

For services, the time saved by one request can be magnified when it reduces queueing. The reverse is also possible: a more expensive cache or a larger batch improves one benchmark but increases contention at peak traffic. Google's _The Tail at Scale_ explains why rare delays matter in large services.[^tail]

Test representative arrival rates, not only a single request in an otherwise idle process. Keep error rates and cancellations visible. A server that rejects slow requests can appear faster unless the result includes those failures. For a UI, inspect the next action as well as the optimized action so deferred work cannot disappear from the accounting.

After release, compare the same journey by build, device class, and cache state. If local gains do not appear in production, inspect the assumption that failed: a different bottleneck, an unrepresentative fixture, or another resource on the critical path. Keep a change because the evidence supports it, not because the agent spent many iterations producing it.
